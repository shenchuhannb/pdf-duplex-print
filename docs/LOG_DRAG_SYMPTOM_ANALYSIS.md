## 1. 症状

- 只在拖动窗口内部的日志分隔条（含中间握把）时出现；拖动窗口边框缩放时正常。
- 快速拖动时，文件列表空状态区域、日志标题条出现白色或旧像素块；日志框看起来在追赶鼠标，伴随轻微抖动。
- 停止拖动后自行恢复，说明布局最终状态没有错误。
- 拖动越快越明显，慢速拖动明显减轻。
- `stacked`、`split` 两种布局，100%、150% 两档缩放都可以出现。

用户原话：

- “单独缩放日志栏时，圈起来这些地方动态显示异常，恢复静止后显示恢复正常，缩放过程中日志栏的框也是抖动的。”
- “故障依旧，快速缩放不行，关键是在边框缩放时正常，单独缩放时不正常。其他成熟应用不会出现这种情况。”

## 2. 复现与观察方式

- 前台复现：按住日志分隔条或中间握把快速上下拖动，不走窗口边框。
- 无可见窗口条件下可以验证的部分：
  - 透明窗口（`alpha=0`）下的几何断言：日志上沿、底边、预览画布宽度和父容器边界；
  - `PrintWindow(PW_RENDERFULLCONTENT)` 静态截图：最终渲染和拖动指示物是否存在；
  - 单元测试驱动的事件处理、排版同步次数、整树失效次数。
- 无法离屏验证的部分：拖动过程中的逐帧残影和撕裂。`PrintWindow` 取到的是完整重绘结果，取不到屏幕合成过程中的中间帧，因此这一层只能由用户前台观感确认。

## 4. 根因判断（待前台方案验证）

Windows 上 Tk 的每个控件都是独立 HWND。内部拖动改变日志抽屉高度后，grid 用 `SetWindowPos` 移动、缩放一串子窗口；系统只按暴露区域产生增量脏区，各子窗口分别重绘。鼠标事件可达 125Hz，Tk 事件循环优先处理输入，几何连续变化时并非每个子窗口都能在下一次几何变化前完成重绘，屏幕上就会出现“新几何 + 旧像素”的混合帧。

窗口边框缩放由系统对整个窗口做失效处理，内容重排集中在少数几次，所以看起来干净。这个差异与“内部拖动 + 局部脏区 + 高频输入”吻合。

该判断能解释：

- 为什么只在快速拖动时明显：重绘被输入事件挤压；
- 为什么停止后恢复：最终一次完整重绘；
- 为什么布局断言全部通过：问题在绘制原子性，不在布局结果。

尚不能解释或未验证：

- 具体哪些子窗口先画、哪些滞后；
- 日志 `Text` 自身是否参与残影；
- DWM 重定向表面是否保留了旧内容；
- 窗口边框缩放时内容排版的真实时序（推测为系统失效 + 集中重排）。

## 6. 后续可选方案

按侵入性从低到高：

1. **保持现状**：接受内部快速拖动的瞬时残影；窗口边框缩放不受影响。
2. **整帧提交**：拖动时对根窗口 `WM_SETREDRAW(0)`，应用高度后 `WM_SETREDRAW(1)` 并用 `RedrawWindow(... | RDW_UPDATENOW)` 强制完整重绘，以 30Hz 左右的上限换取完整帧。保留实时反馈，但每帧约 15–20ms，是否发滞需要前台确认。
3. **`WS_EX_COMPOSITED`**：给顶层窗口开启子窗口双缓冲，理论上直接消除撕裂；已知可能导致整体变慢、黑帧或与分层窗口交互异常，且透明窗口下无法可靠离屏验证，必须在真实窗口测试。
4. **延迟落定 + 可接受的手柄**：沿用 Tk 经典 PanedWindow 的 `opaqueresize=0` 思路，但把预览做成与现有分隔条完全一致的浮动握把，或直接移动真实握把；视觉效果需用户确认。
5. **改用原生 PanedWindow**：把工作区与日志放进 `ttk.Panedwindow` / 经典 `PanedWindow`，由 Tk C 层处理 sash；可能仍有重绘问题，且要重构布局与现有测试。

- 不弹可见窗口、不抢焦点、不前台截图；使用 `alpha=0` 窗口、`PrintWindow`、几何断言和单元测试。

## 8. 结论

症状更像“拖动期间的重绘原子性问题”，不是布局阈值或事件频率本身。仅靠守卫、去重、延迟应用不能保证每个可见帧完整；要彻底消除，需要整帧提交或系统级双缓冲，二者都必须做真实窗口验证。

## 9. CodeArts 修复与防复发记录（2026-11-22）

### 根因类别

跨层绘制契约问题（Cross-Layer Contract）：Tk 的 grid 几何提交是 idle 工作，而 Win32 各子窗口分别绘制。旧拖动入口只修改高度，没有保证“布局全部完成后再呈现完整帧”，因而快速输入时可能出现新几何与旧像素混杂。

### 已实施修复

- 仅在日志分隔条拖动路径增加整帧提交，不改变窗口边框缩放、日志自动增高、工作区密度或打印逻辑。
- 修改高度前向顶层窗口发送 `WM_SETREDRAW(0)`；调用 `update_idletasks()` 完成 grid 与 `<Configure>` 回调；在 `finally` 中发送 `WM_SETREDRAW(1)`，再用 `RedrawWindow(RDW_INVALIDATE | RDW_ERASE | RDW_ALLCHILDREN | RDW_UPDATENOW)` 同步重绘整棵子窗口树。
- 非 Windows 或无法取得顶层 HWND 时保留原有高度修改路径；没有新增运行时依赖，也没有恢复被否决的指示线。

### 为什么此前修复未闭合

- 节流、冻结密度和预览只减少排版工作量，没有约束整窗绘制原子性。
- 指示线通过延迟排版绕开问题，但视觉形式被用户否决，不能作为最终交付。
- 原有几何测试只能证明最终布局正确，无法发现绘制时序缺失。

### 防复发与验证

- `test_log_sash_drag_commits_complete_frame` 锁定“关闭重绘 → 修改高度 → 完成 idle 布局 → 恢复重绘 → 全子窗口同步呈现”的严格顺序和标志位。
- 原有 `stacked` / `split`、100% / 150% DPI 几何回归继续保留；完整测试结果为 `124 passed`，语法检查、隐藏自检和 `git diff --check` 通过。
- 离屏测试不能观察 DWM 合成过程中的逐帧撕裂，也不能证明同步重绘的主观流畅度；最终仍需用户通过 CodeArts 桌面快捷方式做真实前台快速拖动确认。
- 同类高频内部几何调整若出现新旧像素混杂，应先检查绘制提交契约，不要仅增加节流或修改布局阈值。
